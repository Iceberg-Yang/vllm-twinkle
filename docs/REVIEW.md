# 材料审阅与 GitHub 归档建议

审阅日期：2026-09-29。对象是作者的文章及实验配套，不是对两个上游框架的完整代码审计。

## 结论

**适合作为同一个技术实践合集仓库，原目录不宜直接整体上传。** nano-vLLM 的七篇学习顺序清晰，Twinkle 具有明确的端到端实践主线；主要问题不是缺少内容，而是主稿、旧稿、个人规划、上游 checkout 和可复现实验混在一起，且部分文字的确定性超过了证据。

本合集将“能否备份到 GitHub”与“能否宣称是已验证教程”区分开：在确认内容权利后可以上传归档；标记为草案的 Notebook、服务原型与横评不能因此宣传为全部跑通。公开发布还需确认图片/工作相关稿件权属，私有备份不需要先为全部原创材料指定开源许可。

## 内容与结构评价

| 材料 | 合理之处 | 应明确的边界 |
| --- | --- | --- |

| Twinkle | 数据选择、长度报错、训练、保存、加载的闭环完整 | 小样本加两题采样只验证流程，不能证明法律能力或稳定风格提升 |
| 仓库结构 | 两个主题各自有导航、正文、代码，统一根索引 | 不应把官方完整仓库嵌进文章仓库，也不需要为个人合集堆叠贡献规范模板 |

Twinkle 原稿有 13 节，逻辑可以保留；仓库 README 承担安装与运行入口，主文承担经验叙述，观察记录承担历史细节，避免读者把行动大纲当作最新教程。nano 第 01 篇只保留系列主稿，不混入另一版不同 workload 的旧结果。

## 原材料中的重要问题

| 问题 | 原位置 | 对使用的影响 |
| --- | --- | --- |
| 真实凭据与个人 checkpoint | Twinkle 原 `.env`、`inference.py` | 原目录不能直接上传；合集不含 `.env`，checkpoint 已换成运行时配置或脱敏格式 |

| LoRA 效果归因过强 | Twinkle 主文结论 | 40 条输入实际剩 32 条，非确定性采样及输出截断均是混杂因素；已改为观察性结论 |

## 本次归档处理

创建独立上传候选目录，原始材料保留不动。统一每篇 `article.md` / `main.ipynb` 入口，补充主题说明、来源提交与发布前检查脚本。7 份 Notebook 的输出与执行计数均已清空，并通过最终静态检查，防止修改后的代码仍附着旧输出。01 的两张历史实验截图保留，并按历史证据说明。源码克隆改用独立的 `upstream/nano-vllm` 路径，避免与合集主题目录重名。

Twinkle 示例统一读取空白 `.env.example` 对应配置、保护 `--help` 和 import 不触发工作、显式区分 base/LoRA、复用采样客户端、保存完整同题响应；输出路径已存在时拒绝继续。正文去除个人路径与真实任务标识，增加数据传往远端的说明。

没有更改第三方许可证，没有复制上游 `.git`，没有创建远端仓库、Git 提交、公开发布或消耗远端训练资源。已初始化一个空的本地 `main` 分支，并实际验证 9 项 Git 忽略规则：凭据/运行产物被排除，空白配置样例、结果说明和截图可提交。45 个选入文件的原件 SHA-256 均与整理前一致。

## 验证方法与边界

本地可重复检查：

```bash
python3 scripts/check_repository.py
python3 -m unittest discover -s twinkle/examples -p 'test_*.py'
python3 -m unittest discover -s nano-vllm/experiments/benchmarks -p 'test_*.py'
```

静态检查覆盖 Python AST、Notebook JSON 与非 magic Python 片段、Shell 语法、本地 Markdown 文件链接、常见明文凭据格式、个人绝对路径及大文件。它不会执行 Notebook 安装命令，不会验证外部链接和 Markdown 锚点，也不是覆盖所有秘密格式的专业扫描器。

本轮本地验证结果：

| 检查 | 结果与范围 |
| --- | --- |
| 全库静态检查 | 58 个候选文件；17 个 Python 文件、7 份 Notebook 的 96 个 Python 单元、96 处本地文件链接和 1 个 Shell 脚本检查通过；涉及 magic/shell 的单元按脚本中声明的有限规则处理 |
| 内嵌脚本与 CLI | 5 段 Notebook 内嵌 Python 子脚本 AST 通过；11 个命令行入口的 `--help` 成功 |
| Twinkle 隔离测试 | 23 项复跑通过，覆盖无副作用导入、配置、模拟训练/采样、结果保存及防覆盖 |
| benchmark 隔离测试 | 53 项复跑通过，覆盖离线 runner 参数与失败记录、HTTP/chat/SSE 错误和截断、混合单位及汇总；使用内存 mock，不是实际服务压测 |
| 第 07 篇编排 | dry-run 生成 48 个命令但不启动引擎；6 种完整性场景和重跑生成新 session 的内存验证通过，未生成实验结果文件 |
| Markdown | 17 份 Markdown 经解析器内存渲染；文件链接另由静态脚本检查，不等同于 GitHub 页面视觉验收 |
| 原材料 | 45 个选入原件的 SHA-256 再次核对一致 |

实际修改包括显式核验 nano dtype、限制 Transformers 单 GPU、独立预热输入、失败落盘并返回非零退出码、保留服务错误明细、分开统计不同输出单位，以及将调用进程显存口径明确标成 GiB。服务客户端与汇总脚本已另行只读复核。第 07 篇的 dry-run 开关只控制 benchmark 子进程，依赖安装及模型下载仍可能联网，文中已说明。

所有 PNG 已通过格式检查并查看拼图；两张实验截图另行按原图查看。历史吞吐的计算 `133966 / 59.63317608833313` 与 2246.50 output tok/s 相符。创空间历史评估文件通过现有 schema/记录验证脚本；这仅说明记录结构有效，不代表评估结论可以部署。以上没有真实 GPU、远端推理、训练或部署验收。

## 仍需完成的技术验证

1. 在目标 Linux/NVIDIA GPU 上从干净环境顺序执行每篇 Notebook，记录 Python、驱动、Torch、各框架提交、模型/数据 revision。锁定当前服务支持信息，而不是依赖历史配置。
2. 补全四框架同机、相同输入/输出长度及明确缓存状态的多次实验，保留逐次记录、失败和有效配置；单独采集 worker/整卡显存，不能用调用进程峰值代替。
3. 在线 benchmark 明确首非空文本 chunk、usage token 与 chunk 近似的不同口径。socket 操作超时不是严格请求总时限；成功请求的 p95 不能代替含失败的用户体验指标。
4. 06 的 Studio 草案仍需修复就绪探测超时、双进程监督、空 choices、上下文预算、错误提示和访问控制，再做 Docker 构建、GPU 冷启动/缓存重启与对话验收。目前不建议直接公开部署。
5. Twinkle 补全当前服务准入、基础模型和模板兼容性、真实 base/LoRA 输出及独立测试集。法律输出应经适当专业评价；本仓库不支持实际法律决策。
